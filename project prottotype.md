## 1. The challenge (what the judges want)

For **any `account_id`** a judge picks live, the engine must:
1. **Know the customer:** income, bills and fixed costs, savings buffer, months of runway.
2. **Take a shock:** job loss with EI, higher rent/bills, surprise repair, or a mix, with adjustable size.
3. **Make a plan:** a goal plan (e.g. emergency fund) and a backup plan if the shock hits, both from the customer's own numbers.

Judging: **Discovery 35% · Data Use 25% · Communication 25% · Impact 15%.**
Demo: 1 min pitch → 3 min live twist (judge picks an `account_id` + reads a twist card) → 1 min Q&A.
Submission: demo video, **public code repo**, short write-up, links to all outside sources.

**Non-negotiables**
- Judge numbers must match the official formulas **exactly** (§5). Never replace them; our own metrics sit **beside** them.
- Every one of the 4,500 accounts must return a valid result under every shock without errors.
- One command rebuilds everything from the raw CSVs: `docker compose run --rm pipeline`.


| `transactions.csv` | 1,056,320 | `amount` always positive; `signed_amount` +in/−out. Same-day rows not in time order. Read `partner_bank` as VARCHAR. Use only for drill-downs |

## 5. Judge definitions — MUST match exactly

Per account, from `monthly_summary`:

| Symbol | Name | Definition |
|---|---|---|
| **I** | Typical money in | `median(money_in)` over all months |
| **F** | Fixed costs | `median(household_bills + insurance + loan_payments)`. Displayed only, **not** used in runway |
| **S** | Typical spending | `median(money_out)` |
| **H** | Household bills | `median(household_bills)`. Rent/utility shocks scale this |
| **B** | Buffer | `avg(avg_daily_balance)` over the account's **last 6 rows ordered by month** |
| **P** | Loan payment | `loans.monthly_payment` if `status IN ('C','D')`, else 0 (verified identical to start + duration > 2025-12-31) |

**Runway:**
```python
buffer_left = B - one_off_costs
gap = spending_after_shock - income_after_shock
if buffer_left <= 0:  runway = 0.0
elif gap <= 0:        runway = None   # display "no shortfall (120+)"
else:                 runway = min(buffer_left / gap, 120)
runway = round(runway, 1)
```

**Twist → formula mapping:**
| Twist | income_after | spending_after | one_off |
|---|---|---|---|
| Job loss, EI 55% | 0.55 × I | S | 0 |
| Bills +15% | I | S + 0.15 × H | 0 |
| Repair = 1 month of spending | I | S | S |
| Job loss + bills +15% | 0.55 × I | S + 0.15 × H | 0 |

**Verified SQL** (reproduces the pandas reference with max error 0.0 for I/F/S/H/P and 1e-11 for B on all 4,500 accounts):
```sql
WITH last6 AS (
  SELECT account_id, avg(avg_daily_balance) AS B
  FROM (SELECT *, row_number() OVER (PARTITION BY account_id ORDER BY month DESC) AS rn
        FROM staging.stg_monthly_summary)
  WHERE rn <= 6 GROUP BY 1),
agg AS (
  SELECT account_id,
         median(money_in) AS I,
         median(money_out) AS S,
         median(household_bills + insurance + loan_payments) AS F,
         median(household_bills) AS H
  FROM staging.stg_monthly_summary GROUP BY 1)
SELECT a.*, l.B,
       coalesce(CASE WHEN lo.status IN ('C','D') THEN lo.monthly_payment END, 0) AS P
FROM agg a JOIN last6 l USING (account_id)
LEFT JOIN staging.stg_loans lo USING (account_id);
```

## 6. Warehouse design

Three schemas in one DuckDB file: `raw`, `staging`, `marts`. SQL files are numbered and executed in filename order by `pipeline.py`. Each file is idempotent (`CREATE OR REPLACE`).

### 6.1 `raw` (sql/00_raw)
- One table per CSV, loaded with `read_csv(..., header=true)` and explicit types where it matters: `month` VARCHAR, `partner_bank` VARCHAR, dates as DATE.
- `transactions`: `pipeline.py` first converts the CSV → `data/raw/transactions.parquet` (if not already present), then `raw.transactions` reads the Parquet.
- No transformations in raw.

### 6.2 `staging` (sql/10_staging): clean and typed, one table per source
| Table | Key changes |
|---|---|
| `stg_monthly_summary` | add `month_date DATE` (first of month), `fixed_costs`, `discretionary = cash_withdrawals_genuine + card_withdrawals + transfers_out_other`, `net_flow = money_in - money_out` |
| `stg_accounts` | types only |
| `stg_clients` | `age` at `REFERENCE_DATE = 2025-12-31` |
| `stg_dispositions` | types only |
| `stg_account_owner` | one row per account: the owner's client_id, gender, age (test: exactly one owner per account) |
| `stg_cards` | join to dispositions → `account_id`; keep best card per account (gold > classic > junior) |
| `stg_loans` | add `is_running = status IN ('C','D')`, `loan_end = loan_start + duration_months months`, `start_month` VARCHAR |
| `stg_districts` | types; keep NULLs for district 69 |
| `stg_standing_orders` | `purpose` blank → `'other'` |
| `stg_transactions` | from parquet; `date` DATE; `month` VARCHAR |

### 6.3 `marts` (sql/20_marts): star schema + analysis marts
**Star schema**
- `dim_district`: district attributes.
- `dim_account`: account_id, district_id, region, account_opened, owner gender/age, n_users (count dispositions), has_card, card_type, has_loan, loan_status, loan_amount, monthly_payment, loan_start, loan_end, defaulted.
- `fact_account_month`: grain = account × month, all `stg_monthly_summary` measures + `fixed_costs`, `discretionary`, `net_flow`, `is_lean_month` (money_in < 0.55 × account median I).

**Analysis marts**
- `mart_customer_profile`: one row per account. **The engine reads only this table.**
  - Judge numbers: `I, F, S, H, B, P`
  - Context: `n_months, first_month, last_month, D` (= median discretionary), `I_p25` (= `quantile_cont(money_in, 0.25)`)
  - Risk features: `income_cv` (stddev_samp / avg of money_in; NULL if avg = 0), `lean_month_share`, `pension_share` (sum pension_in / sum money_in), `cash_share`, `ever_negative` (any days_below_zero > 0), `neg_days_total`, `balance_slide` (last month avg_daily_balance ÷ max avg_daily_balance of the previous 12 months)
  - Flags (booleans): `flag_volatile` (income_cv > 0.45, the top-quartile cut), `flag_pensioner` (pension_share > 0.30), `flag_overdraft_history` (ever_negative), `flag_balance_slide` (balance_slide < 0.50), `flag_loan_in_debt` (loan_status = 'D'), `flag_short_history` (n_months < 18), `flag_stale` (last_month < '2025-12'), `flag_negative_buffer` (B <= 0), `flag_zero_income` (I = 0)
  - Put all thresholds in `config.py` and also in a `marts.config_thresholds` table so SQL and Python agree.
- `mart_loan_preloan`: one row per loan: features computed **only from months before `start_month`**: pre_n_months, pre_I, pre_S, pre_avg_balance, pre_min_balance, pre_neg_days, pre_income_cv, payment_to_income (= monthly_payment / pre_I), buffer_months (= pre_avg_balance / pre_S), plus `defaulted`, `status`. This is the leakage-free table for default analysis.
- `mart_default_drivers`: default rate + count by quartile of pre_income_cv, payment_to_income, buffer_months, and by pre_neg_days > 0.
- `mart_balance_slide`: for each defaulted account, avg_daily_balance relative to the trailing-12-month max for k = 1..12 months before its first negative month; plus the median by k.
- `mart_findings`: one row per headline number (finding_id, metric, value, n). Feeds `reports/findings.md`.

### 6.4 Quality checks (sql/90_quality): each returns violating rows; pass = 0 rows
- `money_in` and `money_out` identities hold (abs diff > 0.01).
- No duplicate (account_id, month) in `stg_monthly_summary`.
- Every account in accounts has monthly_summary rows; every loan account exists in accounts.
- Exactly one owner per account.
- `mart_customer_profile` has exactly 4,500 rows, no NULL in I, S, F, H, B, P.
- `loans.amount ≈ duration_months × monthly_payment` (abs diff < 1).
- Row counts of raw tables match §4.

## 7. The engine (`src/tangerine/engine.py`)

Pure Python, no UI code. Loads `marts.mart_customer_profile` once into a dict keyed by account_id (cache it), so calls are instant.

```python
@dataclass
class Shock:
    income_factor: float = 1.0       # 0.55 = job loss with EI at 55%
    duration_months: int | None = None  # months the income_factor applies; after that income_after_months applies. None = forever (judge formula)
    income_after_months: float = 0.0 # factor after EI ends (0 = no income)
    bills_increase_pct: float = 0.0  # 0.15 = household bills +15% (applied to H)
    one_off_cost: float = 0.0        # dollars
    one_off_months_of_spending: float = 0.0  # alternative: N × S

PRESETS = {  # the judges' example twists
  "job_loss_ei55":        Shock(income_factor=0.55),
  "ei55_6_months":        Shock(income_factor=0.55, duration_months=6),
  "bills_up_15":          Shock(bills_increase_pct=0.15),
  "furnace_1_month":      Shock(one_off_months_of_spending=1),
  "job_loss_plus_bills":  Shock(income_factor=0.55, bills_increase_pct=0.15),
}
```

Functions:
1. `get_profile(account_id) -> dict`: judge numbers + flags. Raises a clear `UnknownAccount` error for IDs not in the data.
2. `judge_runway(profile, shock) -> RunwayResult`: §5 formula exactly. Returns `months` (float or None), `label` ("4.2 months" / "no shortfall (120+)" / "0 — buffer already gone"), `income_after`, `spending_after`, `gap`, `buffer_left`.
3. `simulate(profile, shock, horizon=24) -> DataFrame`: month-by-month balance path starting at `B - one_off`, with columns month_idx, income, spending, balance, for **both** baseline (no shock) and shocked. Handles `duration_months` (EI for 6 months, then `income_after_months`). `months_until_zero` = first month balance < 0 (None if never within horizon). This is what a chart will plot later.
4. `stress_runway(profile, shock)`: same as judge formula but income = `I_p25` × factor (a lean month, not a median month). Our "check-engine" number, shown beside the judge number.
5. `make_plan(profile, shock) -> Plan`:
   - **Target buffer** = `S × target_months`, where target_months = 6 if `flag_volatile` else 3 (constants in config).
   - **Goal plan:** surplus = I − S.
     - If surplus > 0: save `min(surplus, 0.5 × surplus + 0.1 × D)` per month (round to $10); months_to_goal = ceil(max(target − B, 0) / saving).
     - If surplus ≤ 0: required saving comes from cutting discretionary spending D; report the % cut of D needed to save enough to reach the target in 12 months.
     - If B ≥ target: "goal already met". Suggest keeping it and the months of cover it gives.
   - **Backup plan (if the shock hits):** keep household bills, insurance and loan payments fixed; cut discretionary D by a default 30% (adjustable). Report the new spending, the new judge-formula runway, and the cut needed to reach 6 months of runway (or "not reachable by cuts alone").
   - **Context notes** (strings): pensioner (job-loss/EI shock may not apply), loan ends on date X (P frees up), loan status D, negative buffer (step 1 = exit overdraft), short or stale history.
6. `run(account_id, shock) -> dict`: one call returning profile, judge_runway, stress_runway, simulation, plan, notes. JSON-serialisable (the future app and an AI agent both call this).

Rules:
- Never divide by zero (I = 0, S = 0, D = 0 cases).
- Never return `inf` or `NaN` to callers.
- Money rounded to 2 dp, runway to 1 dp, at the output boundary only (keep full precision internally so parity holds).

## 12. Conventions

- SQL: lowercase keywords are fine, but be consistent; one model per file; filename = table name with number prefix (`20_mart_customer_profile.sql`); `CREATE OR REPLACE TABLE schema.name AS ...`; comment the grain at the top of every model.
- Python: type hints, small pure functions, constants in `config.py`, no hard-coded paths.
- Never load `transactions` for profile metrics; `monthly_summary` already aggregates it.
- Medians include quiet (zero) months; `monthly_summary` already contains them, so do not filter them out.
- Keep judge numbers and our numbers side by side, clearly labelled ("Judge formula" vs "Stress-adjusted").
- Every number in the pitch must trace to a mart or `findings.py` output.
- If anything here conflicts with `data/raw/README.md` (official brief), the brief wins. Flag the conflict instead of guessing.
